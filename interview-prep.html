4Why each choice — memorise these

  1. Morning brief, not a chat interface

    Why Founders don't bother asking cross-tool questions — they run on vibes. A chat interface requires knowing what to ask. The brief is pushed every morning with no input from them. Chat is only for follow-up.
    One-liner Push beats pull.

  2. Deterministic SQL for decisions, LLM only for words

    Why Cost (10k merchants × chain-of-thought is expensive), auditability (same input → same output, always), and trust (LLM decisions can drift between runs). The LLM writes the explanation. SQL makes the flag.
    One-liner LLM for narrative. SQL for decisions.

  3. Provenance as a database constraint, not a convention

    Why NOT NULL foreign key to raw_payloads on every row. Postgres enforces it. The Citation Inspector in the UI just surfaces what's already guaranteed at the schema level — you can click any number and trace it to the exact API payload.

  4. Five agents instead of one

    Why More than one agent produces genuine disagreement on the same target — more useful than one always-agreeable agent. Rishi and Meera flagging the same adset for different reasons is signal you can't get from a single agent.

  5. Google Ads as a 5th connector

    Why Not to hit a number — it unlocked a new question: "for the same SKU, which channel is more efficient per rupee?" On demo data, Google Search outperforms Meta lookalikes on Cobalt Tee. That question didn't exist before.

  6. hire() autonomous mode off by default

    Why Unbounded recursive agent spawning is how demos go wrong. Autonomous mode fires only when the same target is flagged 3+ consecutive runs, limited to 1 hire per run, never the same target twice, full audit trail. Safety constraints came before the feature.

  7. No multi-agent framework (no LangChain)

    Why Frameworks make it easy to chain LLM calls but don't give you citation enforcement, audit trails, or a deterministic decision core. The agents here don't need a framework — they need SQL and a contract.

5Limitations — be upfront

  • INR only.
    Multi-currency merchants would silently misaggregate. V1 task.
  • Last-click UTM attribution.
    iOS14 dark social, view-through, multi-touch all missed. Rishi declares this in every proposal.
  • COGS defaults to 40% proxy.
    Unless the founder uploads a CSV. Every agent declares which mode it's running in.
  • Partial returns not modeled.
    RTO yes. Shopify refunds outside the order flow, no. Aanya's margin is an approximation.
  • Trust scorecard is replay-on-synthetic-data, not causal.
    Real grading needs counterfactual evaluation — what would have happened if the founder hadn't acted? That's an ML research problem, not a coding task.
  • Cross-tenant isolation is session-bound merchant_id, not Postgres RLS.
    Fine for v0, needs hardening at scale.
  • Citation escape hatch.
    If the model hedges ("approximately"), an uncited number can slip through the validator. V1 fix.
  • hire() is parameterized, not free-form.
    Three template shapes. "Hire an analyst who reads ad creatives" is v1.

6Questions they'll ask

Why a morning brief instead of just a chat interface?
Founders don't bother asking cross-tool questions — they run on vibes. A chat interface requires knowing what to ask, which founders don't. The brief is pushed every morning with no input from them. Chat is the follow-up surface for when they care about something specific. → Push beats pull.
How does the citation contract actually work?
Three layers: (1) system prompt tells the model every numeric claim must end with [cite:table:rowid]. (2) A server-side validator re-fetches each cited row, checks it belongs to this merchant, and rejects the response if any number is uncited. (3) The schema enforces a NOT NULL foreign key to raw_payloads on every row — so citations always trace back to real data, they can't be invented. → Can't insert without provenance. It's enforced at the DB level.
Why deterministic SQL decisions, not LLM reasoning?
Cost (10k merchants × chain-of-thought is expensive). Auditability (same input → same output, always). Trust (LLM decisions drift between runs; founders need a consistent track record). The LLM only writes the human-readable explanation. The actual flag logic is SQL with hand-written rules. → LLM for words. SQL for decisions.
Why not use LangChain or a multi-agent framework?
Those frameworks make it easy to chain LLM calls, but they don't give you audit trails, citation enforcement, or a deterministic decision core. The agents here don't need a framework — they need SQL and a contract.
How would you scale this to 10,000 merchants?
I know three specific bottlenecks. Meta API rate limits — 200 calls/hr/account, needs per-account token rotation and queued async jobs. raw_payloads archive — ~5GB/day at sustained sync, needs cold storage to S3 + DuckDB. Webhook fan-in at peak — v0 polls, which doesn't scale, needs Kafka or similar. The agent runs themselves are cheap at ~6ms each, so 5 agents × 10k merchants daily is about 5 minutes of CPU. → Agent runs are cheap. Data infrastructure is the problem.
Why RTO-focused instead of just revenue analytics?
Indian D2C has a 25–30% COD RTO problem that wipes out gross margin — and generic analytics tools miss it entirely. The founder's dashboard shows ROAS. It doesn't show "this adset is driving orders that mostly don't get delivered." That cross-tool join is what nobody does in Excel. Shiprocket owns that fulfillment data — which is exactly why this framing made sense for this company.
What would you do with another week?
Counterfactual evaluation — proving a proposal would have actually saved money if the founder had acted on it. Right now the trust scorecard replays synthetic data. Real grading needs a simulator that asks "what would have happened without this action?" That's an applied ML research problem, not a coding task. That's the most interesting unsolved thing.
Why five agents instead of one?
Once you have more than one agent, you get genuine disagreement on the same target — which is more useful than one always-agreeable agent. The Rishi-Meera disagreement on the Crimson Tee adset (different reasoning, same conclusion) is signal you can't get from a single agent.

8How an agent is structured

Every agent is an AgentSpec object — a plain TypeScript object, not a class, not a framework. It has four things:

AgentSpec shape

name / role — display identity ("Rishi", "Growth Lead")
systemPrompt — personality string passed to the LLM only for narration
decide(ctx) — the deterministic function. Runs SQL, computes numbers, returns proposals. No LLM call here.
declaredFailureModes — list of known limitations shown in the UI on every proposal

The flow for one agent run:

  1. decide() runs SQL

    What Plain SQL via Drizzle ORM. Aggregates the normalized tables (orders, shipments, ad_spend_daily, products, ad_attributions). All the math happens here — no LLM.

  2. decide() returns ProposalInput[]

    What Structured objects with: action_type, target_entity_id, expected_savings_inr, confidence (0–1), caveats[], citation_row_ids[], prediction (metric, direction, window_days).

  3. narrate() writes the words

    What If ANTHROPIC_API_KEY is set, calls claude-haiku with the systemPrompt + the ProposalInput JSON. Told: "write 2-3 sentences in your voice. Do NOT invent any numbers — only restate what's in the input." Falls back to a deterministic template if the LLM call fails.

  4. Proposal saved to DB

    What Upserted into the proposals table with the agent_run_id, so autonomous-hire logic can check how many consecutive runs have flagged the same target. Status transitions: pending → superseded (not deleted) so history is preserved.
The systemPrompt gives the agent its voice — "Hindi-English bilingual mindset, fulfillment-obsessed" (Meera), "no-nonsense, skeptical of ROAS-on-paper numbers" (Rishi). The decision is never touched by this prompt. Only the narrative explanation is.

10Scalability tools — what they are

Three tools mentioned in the README. Here's what each one actually does and why it solves the specific bottleneck.

Kafka — what is it and why do we need it?
What it is: a message queue. You publish events ("this order just arrived") to a topic, and multiple consumers can read them independently and at their own pace.

The problem it solves: v0 polls the APIs on a cron — every connector calls Shopify/Meta/Shiprocket every N minutes. At 10k merchants, that's 10k × (polling interval) API calls hammering the same endpoints. With Kafka, each merchant's connector publishes events as they arrive (via webhooks), and the sync workers consume them from the queue. No polling, no rate-limit pile-up, and if a worker crashes it picks up where it left off (Kafka retains the message). → Polling doesn't scale. Kafka turns 10k simultaneous syncs into 10k events in a queue.
S3 — what is it and why do we need it?
What it is: Amazon's object storage. Cheap, infinitely scalable storage for files/blobs. Postgres is not designed for storing huge volumes of raw JSON payloads long-term.

The problem it solves: the raw_payloads table stores every raw API response — Shopify orders, Meta insights, Shiprocket shipments. At 10k merchants that's ~5GB/day. After 90 days that's 450GB in Postgres, which is slow and expensive. The plan: keep only the last 30 days of raw_payloads in Postgres (for citations). Archive older data to S3 as compressed JSON. The citation contract still works because recent data is in Postgres; historical data is queryable via DuckDB. → Postgres for hot data (citations). S3 for cold archive (history).
DuckDB — what is it and why does it pair with S3?
What it is: an in-process analytical database — think SQLite but for analytics. It can query Parquet files on S3 directly without loading them into memory first. No separate server needed.

The problem it solves: once raw_payloads are archived to S3, you still need to query them — for historical trend analysis, for counterfactual evaluation, for agent training data. DuckDB can SELECT FROM 's3://bucket/payloads/*.parquet' directly, and it's fast (columnar storage, vectorized execution). You run it as a library inside the agent process — no infra to manage. → DuckDB reads the S3 archive without needing a data warehouse.
Token rotation — what is it?
The problem: Meta's API allows 200 calls/hr per OAuth token. At 10k merchants, if every merchant has a separate token, that's fine — but you can't make 10k API calls in the same hour from one token. Token rotation means: pool the tokens, distribute calls across them so no single token hits its rate limit. Each merchant has their own token; the sync scheduler ensures no token is called more than 200×/hr. → One token per merchant. Rate limit is per-token, not global.

11Ask them

  1. How is the AI team structured — dedicated engineers or embedded in product squads?
    Tells you if this is a serious platform bet or a feature bolted onto an existing team.
  2. Is this a standalone product or embedded in the existing merchant dashboard?
    Core bet vs side experiment — determines resourcing, deadlines, and whether you're shipping or researching.
  3. What does Shiprocket's data infrastructure look like across the platform?
    Do you inherit a solid data layer, or do you need to build it first?
  4. What's the bar for a proposal to move from "show the founder" to "execute automatically"?
    Shows you've thought about responsible deployment. Also tells you their risk tolerance.
  5. Which D2C pain points are you still seeing that existing AI tools don't address?
    What they actually want built vs what's in the brief.
  6. What does success look like in the first 90 days?
    Ship features, do research, or build infra? Concrete expectations matter.
  7. How much autonomy do engineers have over design choices?
    Do the "whys" matter here, or just the delivery?
  8. What's the biggest technical challenge you're anticipating as this scales?
    You already have an answer (Meta rate limits, storage, fan-in). See if your concerns match theirs.
